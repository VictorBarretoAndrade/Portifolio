PedidoJSON PT-BR — a fine-tuned LLM that turns food orders into validated JSON

  • Personal project
  • November 2026
  • Qwen2.5-1.5B-Instruct, LoRA (PEFT, TRL), Pydantic, Gradio
  • GitHub
  • Model (Hugging Face)
  • Dataset
  • Demo (Colab)
Why it matters for an AI Engineer role

It is the whole loop of shipping an LLM feature on a delivery problem: synthetic data with labels that are correct by construction, LoRA fine-tuning that fits in 8 GB of VRAM, an evaluation against prompting baselines and on a test set outside the training style, and guardrails so the answer is always a valid order that uses only products from the menu.

A customer types an order in informal Portuguese, with slang, typos, numbers written as words and items the restaurant does not sell. The model gets the menu and the order and returns JSON with items, quantities, sizes, add-ons, removals and notes, plus a list of what it could not find. A product name must be copied exactly from the menu; vague terms such as "a soda" when the menu has several go to the not-found list instead of a guess.

Training: Qwen2.5-1.5B-Instruct + LoRA, 4,000 synthetic orders, 2 epochs, 110 min on one RTX 3060 with the process capped at 8 GB of VRAM.

External test 150 orders in 6 menus of its own, one of them a bakery, a store type that does not exist in training. The orders and labels were written by another LLM, not by my data generator, and I reviewed them by hand. None of them was used in training. They are not real customer orders.

  • 64.7%orders fully right (exact match), vs 11.3% for few-shot prompting
  • 82.7%item-level F1
  • 0%products invented (few-shot: 10.7%)
  • 100%answers that are valid JSON in the schema
  • 7.96 GBpeak VRAM in training (110 min, RTX 3060 capped at 8 GB)

What the numbers say

  • Fine-tuning is what makes it work. With three examples in the prompt, the same base model gets 11.3% of the external orders fully right; with the LoRA adapter, 61.3%.
  • The synthetic test is a ceiling, and I report the drop. Exact match goes from 86.2% on synthetic orders to 64.7% on orders written in another style. The gap measures how much the model leans on the style of my generator.
  • Guardrails make 0% invented products a guarantee, not luck, and add 3.4 points of exact match on the external test. Most of what remains is in add-ons and removals: they are wrong in 39 of the 53 external orders that are not fully right.
  • Limits: trained only on synthetic data, and the external test was written by an LLM, not by real customers. A test with real orders is the next step.

Next steps to close the gap between 86% and 65%

  1. Real orders as the main test set. Collect real customer messages (anonymized, with consent), label them by hand and use them to decide every change below.
  2. Cover what the generator does not write: half-and-half pizzas, combos, corrections in the middle of a message ("no, make it a large one"), "the usual", and orders split over several messages.
  3. More varied training text: mix the rule-based generator with paraphrases written by an LLM and checked against the known label, so the model stops leaning on the generator's phrasing.
  4. Schema-constrained decoding: generate under a JSON grammar whose product field only accepts names from the menu, so invalid output and invented products become impossible instead of being fixed afterwards.
  5. Attack the largest error class first: the model misses add-ons said indirectly ("go heavy on the bacon", "with stuffed crust") and mixes up changes that apply to only one unit ("one of them without mayo"). Add these patterns to the data and track that category on the test sets.

CobotSort AI — simulated collaborative-robot sorting cell

  • Personal project
  • October 2026
  • Python, MuJoCo, YOLO11n, PyQt6
  • GitHub
  • Detector (Hugging Face)
  • Synthetic images
Why it matters for this skill

I built it after the BRICS Hi-Tech Skills Camp to practice every module of the competition end to end, and I report the results in the camp's judging order: safety, degree of automation, precision, speed.

A 6-axis cobot with a vacuum gripper sorts colored cubes into bins. The UR5e model stands in for the ARM95 used in the camp (same class: 6 axes, 5 kg payload). Purple cubes are defects and go to a reject bin. Everything runs in simulation; no number here comes from real hardware.

The four competition modules, rebuilt

  • Module AGUI, semi-automatic sorting

    PyQt6 operator GUI: pick a detected part and a bin, then execute. Manual jog in joint and Cartesian space, vacuum on/off, home.

  • Module BAutomatic sorting

    Park the arm, scan, detect, pick nearest-first, place, re-scan to verify the result; repeat until no sortable part is left.

  • Module VTrain AI object detection

    YOLO11n trained only on synthetic images, labeled automatically from segmentation renders, with randomized lighting, colors, camera pose and distractors.

  • Module GIntegrate the AI

    Detections become table coordinates through a pinhole camera model and drive the pick-and-place.

Why the cell places cubes within 0.91 mm when this table says 1.38 mm: these test images randomize lighting, colors, camera pose and distractors on purpose. Inside the cell the lighting and the top camera are fixed, and the detector's localization error measured at every scan of the 20 episodes is 0.91 mm (HSV: 1.27 mm). The gripper carries that detection error into the bin, so the placement error matches it (0.91 and 1.30 mm); with ground-truth positions it drops to 0.08 mm.

Kinematics, as taught in the camp

  • Forward kinematics with DH parameters: checked against the simulator on 50 random configurations; 0.80 mm RMS position error with Universal Robots' published DH table.
  • Inverse kinematics (damped least squares, several starting points): 100 of 100 reachable targets solved with error below 0.01 mm, on average 7.5 different joint solutions per target. An unreachable target returns no solution.
  • Singularities: motions are blocked when the manipulability index drops below half the lowest value seen in normal operation (calibrated on 22,386 samples).
Operator agent

Same pattern as EduBot: the AI decides what, deterministic code decides how and whether it is safe. 10 of 10 test orders in Portuguese and English passed, including refusing a bin that does not exist, asking back on ambiguous orders and stopping on “pare”. Measured with the deterministic provider; the Claude provider uses the same tools and guardrails.

EduBot — AI agent for personalized learning

  • Project Lead and Tech Lead, team of 8
  • 2026
  • Python/Flask, MySQL, React + TypeScript, Claude via AWS Bedrock
  • GitHub
Why it matters for this skill

It is an AI agent working inside a real system: it acts through controlled tools, its inputs are validated, a rule-based fallback takes over if the model fails, and high-impact actions wait for human approval. CobotSort's operator agent reuses this design.

  • 2nd place — HACKaSTONE 2026 Grand Final
  • Lead-author paper presented — AI for Education NL 2026

2nd place at the Grand Final of HACKaSTONE 2026, a global contest on agentic AI for education (Amsterdam). Lead-author paper on EduBot presented at the Conference AI for Education The Netherlands 2026.

The data loop: student behavior feeds the AI

What I did

  • Led the 8-person team as project lead and tech lead: defined the architecture and integrated back end, front end and AI layer.
  • Tool-use loop on the Anthropic API (Claude via AWS Bedrock) behind an interchangeable provider layer (mock / Bedrock / direct API), with four controlled tools and a rule-based fallback.
  • Guardrails: the student's identity comes only from the session token; record IDs are validated before any tool runs.
  • Python/Flask REST API with 67 endpoints, MySQL with 31 tables, React + TypeScript front end, Docker Compose, 332 automated tests.
